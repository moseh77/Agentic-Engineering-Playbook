Long-form teaching breakdown · Claude Code

Two layers make Claude
build like an engineer, not a vending machine.

This is the full system behind a real, still-running production build done almost entirely through Claude Code — written for anyone who wants to get genuinely good at building with AI, not just prompt it into a demo. It's two stacked layers: a process framework (a chain of skills — scope, architect, develop, check, test, document, sync) that governs how any single piece of work moves from idea to shipped code, and a project contract (AGENTS.md) that gives Claude durable, re-read-every-session memory of this specific codebase's rules. Neither one alone is enough. Together they're the difference between "an AI wrote some code" and a reviewable, auditable engineering process.

01 Where this comes from

The process layer isn't invented here — go get it

The scope → architect → develop → check → test → document → sync chain is a published skill pack, not a private trick. It's taught as the "Agentic Engineering" workflow by Adrian Hajdin at JS Mastery, and it's the thing that turned this project from "a bunch of ad-hoc Claude Code sessions" into something that behaves like a real engineering process over months of continuous work.

Install guides, the full skill set, and the reasoning behind each step live at:
jsmastery.com/workflow-guides →

Practically, these arrive as Claude Code skills — markdown files with a frontmatter description Claude reads to decide when to self-invoke, typically dropped into a skills directory (project-scoped under .claude/skills/, or available globally) and triggered either by name (/scope, /architect…) or automatically when the task shape matches the skill's own description. You don't have to memorize when to call which one — if you phrase your request naturally ("let's plan the next feature," "build this page," "is this ready to ship") the matching skill self-triggers, because its description was written to match exactly that kind of request.

There's also a bootstrapping skill worth knowing by name: /audit. Run it on a greenfield project, or point it at one area of an existing codebase (/audit src/auth), and it writes the first AGENTS.md (plus thin CLAUDE.md pointers) every later skill in this chain then reads. It only adds what's missing — it never overwrites curated content you've already written by hand. That's genuinely the fastest way to start: don't write your contract file from a blank page, audit your way to a first draft and then hand-edit it.

02 The process layer

Eight skills, each owning one phase of the work

This is the part most people skip when they start using AI coding tools — they go straight to "build me X." The entire value of this framework is that it refuses to let you do that. Idea, design decision, implementation, and proof are four different jobs with four different skills, and each one hands off to the next with a real file as the artifact — not a chat message that evaporates when the context window rolls over.

0 brainstorming precursor — always first

Job: explore intent, requirements and design before anything gets built or even scoped. This is the one skill the framework insists on unconditionally — "you MUST use this before any creative work." It's the guard against the single most common failure mode with AI tools: an agent that confidently builds the wrong thing fast.

Trigger
Any new feature, component, or behavior change — before /scope or /architect run
Produces
A clarified understanding — feeds directly into /scope or /architect, not a file of its own
1 /scope WHAT to build

Job: turns a product idea into a living, coarse scope — deliberately not a detailed spec. Plans a new product, plans the next slice of an existing one, enrolls one named feature, or — run with no argument — reconciles the scope against what actually shipped and queues up what's next.

Reads
AGENTS.md, prior scope state
Writes
docs/scope/
Hands off to
/architect for design, /develop for build
2 /architect HOW — the decision owner

Job: runs whenever a load-bearing technical decision is unmade — choosing between approaches, designing a feature or page, picking a piece of the stack, or when /develop itself hits a decision it isn't allowed to make silently and routes back here. Asks deep questions, recommends an answer, and is the sole owner of every spec file — nothing else in the chain is allowed to write one.

Reads
AGENTS.md, docs/scope/
Writes
docs/specs/ — the approved build spec
Triggers on
"should we use X or Y," "how should this be structured," a stack choice
3 /develop BUILD — and refuse to guess

Job: builds a feature, page, component, API, service or data slice from an approved design. Its most important behavior is what it does when a decision is still open and no spec records an answer: it stops and routes you to /architect instead of guessing. When a spec does exist, it reads that spec plus AGENTS.md, builds, and advances the scope state to reflect what shipped.

Reads
docs/specs/, AGENTS.md
Writes
actual source code, plus scope-status updates
Can refuse
Yes — bounces to /architect on an undecided, load-bearing question
4 /check verify PROVE it does what the spec says

Job: drives the real, running app to prove behavior against the spec — every acceptance criterion actually met, every surface actually built. Not a type-check, not a unit test: an agent clicking through the real thing the way a human QA pass would. Runs right after /develop.

Reads
docs/specs/'s acceptance criteria
Writes
docs/reviews/ — never touches code
5 /check review A second, uninvested opinion

Job: a senior code review run on a fresh model — one that did not write the code, and has no stake in defending it. Runs before a PR, not before verify. The point is structural: the model that just spent an hour implementing something is the worst-positioned reviewer of its own work — it's primed to see what it meant to write, not what's actually there.

Reads
the diff, cold — no implementation context carried over
Writes
docs/reviews/ — never edits code
6 /test lock in the behavior

Job: writes the test suite for whatever was just built or changed. Targets the uncommitted diff automatically — you don't point it at files by hand. Reads a saved test preferences.json for your framework of choice (asks once, remembers after), and picks a strategy per file: happy path, edge cases, error states, accessibility — not the same shallow "renders without crashing" test on everything.

Reads
uncommitted diff, saved test framework preference
Writes
real test files, matched to what actually changed
7 /document hand-off prose

Job: drafts a PR description, a changelog entry, or release notes straight from the real diff and commit history, once a change is actually ready to hand off. Output is prose only — it never touches code or runs git commands itself, which matters if (like this project) your standing preference is "give me the git command, don't commit it yourself."

Reads
the real diff and commit log
Writes
prose only — PR body, changelog, release note
8 /sync close the loop

Job: the last step, run after a change actually ships — not when it's merely approved. Makes surgical, line-level edits back into AGENTS.md, the scope docs, and spec statuses, reconciling what the contract file claims against what's actually true. Critically, it never rewrites a whole section or curated prose — it updates status lines, it doesn't restructure your judgment calls.

Reads
what actually shipped vs. what the docs currently claim
Writes
surgical edits to AGENTS.md, docs/scope/, spec statuses
03 Put together

What one real feature actually goes through

Here's the chain end to end, as it plays out on a single piece of work — say, a new automation that needs its own background job, a database table, and a dashboard page.

Brainstorm the idea
What problem is this solving, for whom, and what does "working" actually look like — before anything is written down as a plan.
/scope it
Add it to the living scope doc as the next coarse slice of work. Not detailed yet — just "this is next, here's roughly why."
/architect the load-bearing decisions
Which database shape, which third-party API, sync vs. async, where the logic lives. Written to a real spec file, not left implicit.
/develop against that spec
Implementation happens strictly against the approved spec — if something's still undecided, it bounces back to step 3 instead of guessing.
/check verify
Drive the real app. Does every acceptance criterion in the spec actually hold, for real, right now?
/test
Lock the behavior in so a later, unrelated change can't silently break it.
/check review
A fresh model reads the diff cold, before it goes anywhere near a pull request.
/document
A PR description or changelog entry, generated from what actually changed — not written from memory after the fact.
/sync
The scope doc, the spec, and AGENTS.md all get updated to say what's actually true now. The contract file never goes stale.
✓

Notice what never happens in this chain: Claude writing code because you asked for a feature in one sentence. Every step that touches the filesystem is gated by a step that produced a written artifact first — a scope entry, a spec, test files, a review note. That's the entire trick. It's slower per feature and dramatically faster per month, because nothing has to be re-explained or silently re-decided the next session.

04 The project layer

AGENTS.md — the file Claude re-reads on every request

If the skill chain above is the process every project should run, AGENTS.md is what makes that process actually know this codebase. It's the first thing read, every single time, per this project's own workflow rule — not loaded once and trusted to persist in memory. What follows is the real file from a production multi-agent SaaS, section by section, with why each one exists and what breaks without it.

excerptAGENTS.md · opening lines, verbatim
# AGENTS.md

You are a principal-level full-stack engineer and AI implementation agent
working on [the product] — [one-line identity statement].

Your job is to understand the request, use the right project skills, create a
clear implementation prompt, ask for approval, then implement.

Two things in that opening paragraph are doing real work. First, the role assignment — "principal-level engineer," not "helpful assistant" — sets the bar for what counts as an acceptable answer; it changes how thoroughly Claude inspects existing code before touching it. Second, that last sentence is the entire workflow compressed to one line: understand → use skills → write a prompt → get approval → implement. Every other section in the file exists to make one word in that sentence concrete.

§1
Product

States what the thing is in one sentence, then lists every piece to build — in build order — and keeps that list alive as a running build log: each entry gets annotated in place as phases ship, noting which phase is done, which approved prompt file proved it, and what was deliberately cut from scope. This is the section /sync edits most often — it's the project's own changelog, living inside the contract file instead of scattered across commit messages nobody re-reads.

Just as important as what's listed: a dedicated "explicitly deferred" block at the end, naming work that is not happening yet and why — so an idea that got reasonably rejected in week one doesn't quietly resurface as "obvious scope" in week twelve. 

Build only, in this order:
- [piece 1], end-to-end: background job(s), schema, and the UI surface showing it running
- [piece 2] — full design in docs/specs/<name>.md.
  Phase 1 ([...]) is complete per prompts/<name>-phase-1-[...].md.
  Phase 2 ([...]) is complete per prompts/<name>-phase-2-[...].md.
  No further phases currently planned.

Explicitly deferred — do not build unless the user asks for a new plan first:
- [idea considered and intentionally not built yet, with the actual reason]

Do not overbuild.
§2
Workflow

The eleven-step loop every single request must run — this is where the skill chain from §02 above gets wired directly into project rules, by name. It's the section that turns "an LLM with file access" into something that behaves like a disciplined engineer on a deadline it respects. 

For every implementation request:

1. Read AGENTS.md.
2. Read the skills explicitly mentioned by the user.
3. Read clearly needed supporting skills from §3's locked list.
4. Inspect relevant existing code.
5. Ask a focused question only if the task has meaningful ambiguity.
6. For a new feature/phase: run the platform-capability audit (§12)
   before scoping anything.
7. Create a detailed prompt file in prompts/.
8. Ask: "I prepared the implementation prompt at prompts/<file>.md.
   Is this good to execute?"  ← the hard gate
9. On approval, re-read the approved file and implement it strictly.
10. Run available checks (§15) — check verify against acceptance
    criteria, test for the suite.
11. Share exact steps to test or run the completed feature.

Before merge: check review for an independent second-model read.
After shipping: sync, add a progress-log entry, document
if a PR description or changelog entry is needed.

Do not code before creating the prompt unless explicitly told to skip it.

The line worth re-reading twice is step 8. It's not a suggestion — it's a literal string Claude is instructed to output and then stop. Nothing downstream happens without a human typing "yes." On a project with months of continuous changes, that single gate is what keeps an agency owner, a solo founder, or a team lead from having to review a wall of diffs after the fact instead of a focused plan before the fact.

§3–§4 — the toolbox and the unit of work

§3
Skills

A closed list of the only skills Claude may use on this repo — each with a one-line reason tied to this specific project, not a generic "best practice" blurb. The file states outright: Do not invent new skills. That line matters more than it looks — without it, an agent under time pressure will happily improvise a plausible-sounding approach instead of using the vetted one, and you won't notice until it's already in the codebase. 

Use only these skills:

- trigger-dev — background jobs, scheduling, retries/idempotency
- supabase — schema, migrations, RLS policies, service-role usage
- ai-sdk — any LLM call inside a background job
- frontend-design — loaded before any UI work; this dashboard
  is the portfolio, it can't look like a stock admin template
- check / test / document / sync — the process layer, §02 above

Do not invent new skills. For anything with no dedicated project skill,
use existing project patterns and the vendor's own docs instead.

One more detail worth copying: this project also ships scoped versions of some skills inside .claude/skills/ — project-specific variants that override the generic global skill whenever the files being touched live under this repo. The rule is simple: the project's own conventions always win over a generic default.

§4
Prompt files

The required shape of the plan Claude writes at step 7 of the workflow, before anything gets approved. Ten fields, every time — this is what makes the approval gate meaningful instead of a rubber stamp. Approving a vague paragraph is nothing; approving ten concrete, checkable commitments is a real decision.

Worth noting: this applies even to removing something. When one real integration in this project turned out to be the wrong vendor choice, pulling it back out was itself written and approved as a prompt file — prompts/<agent>-remove-<vendor>.md — not a quiet, unreviewed patch. The gate applies to subtraction exactly as much as addition.

§5–§7 — architecture, stack, and data

§5
Architecture

A hard layering rule, stated once and then never re-litigated per feature:

- UI (pages/components): displays stored data only. Must never
  call a third-party API or contain business logic directly.
- Server actions / thin API routes: the only layer allowed to
  trigger a background job or read/write the database.
- Background jobs: own all business logic, every third-party
  API call, retries, and idempotency.
- Database: source of truth for config, run history, records, logs.

UI must never call the database or a third-party API directly —
always through a server action or a background job.

This single rule is why a feature can be extracted into its own app later, or debugged by a fresh session, without an archaeology project: logic is never smeared across a React component "just this once."

§6
Tech stack

What's in — and, just as load-bearing, what's explicitly out, each with the real reasoning, not just the verdict. This is the section that stops the same architecture debate from reopening six weeks later when someone (human or Claude) half-remembers a tool that got considered. 

Do not use:
- Clerk — rejected in favor of [the chosen auth], already
  free since [the data layer] is the committed choice
- NextAuth — would require bridging externally-issued JWTs
  into [the DB]'s row-level security; real complexity for zero benefit
- A separate backend framework — [background jobs] +
  server actions/API routes are the entire backend
§7
Data model

The shared, source-of-truth tables expected to exist from day one — written so every future feature reuses the same shape instead of inventing its own variant. In this project that's users, agents, integrations (one row per external account connection — an opaque reference only, never a raw credential), automation_runs (one row per job execution), and spend_log (running per-period cost counters). Every new feature's own tables get documented here too, each tagged with which design doc or prompt file explains it — so the schema's history stays legible without digging through migration files.

§8–§12 — the standing rules that can't drift

These are the sections worth stealing wholesale, even if nothing else in this file applies to your project. Each one encodes a mistake that's easy to make exactly once, silently, per feature — until it's written down as a rule every prompt file has to satisfy.

§8
Run logging

Every background job, on every run, writes one row at start (running) and updates it on completion (succeeded/failed, a value-generated figure, error detail on failure). The dashboard only ever reads from this table — it never infers status by polling the job platform directly. This is the rule that makes "show someone the automation is really running" literally true instead of aspirational.

§9
Row isolation

Every table carries an owner column and a row-level security policy from day one — even with exactly one real user in the system today. No query may rely on "there's only one user" to skip an ownership filter. Write every query as if multiple tenants' rows already coexist, because eventually they will. This single discipline is what let this project's single-owner tables become multi-tenant later by adding rows, not by rewriting a single query.

§10
Spend cap

Any job step calling a paid API must check a running spend counter immediately before the call and short-circuit — log it, mark the run failed with a clear reason, skip the call — if the cap for that period is already met. The counter increments on a successful call, in the same step as its own error handling. An unattended, scheduled AI pipeline with no spend cap is a bill waiting to happen; this makes it structurally impossible to forget per-feature.

§11
Depth rule

The single most undersold rule in the whole file, and probably the most generally useful one. Verbatim intent: a technically-working-but-shallow rebuild — "an AI call returns a verdict, upsert a record, done" — undersells the entire thing even if it passes acceptance criteria. Do not ship one. Before writing a prompt file for new automation logic, state explicitly which real decision-making behaviors are being matched or upgraded (multi-signal reasoning instead of one opaque AI verdict, the right system-of-record action, tiered human notification, retry resilience, an audit trail) — and which are being deliberately dropped, and why. This is the difference between a feature that reads as "an LLM call in a wrapper" and one that reads as real engineering.

§12
Platform audit

Before scoping any new feature that touches a third-party platform, check whether that vendor already ships the planned functionality natively — its own docs or in-app settings, not just "the raw API could technically do this." If it does, don't build it; point the user at the platform's own setting, unless there's a concrete reason this app must still own it (its own audit trail, sending from the user's own branded channel, working even when the vendor's native toggle is off) — and state that reason explicitly in the prompt file. This rule directly cancelled real planned work in this project once a vendor's own feature set was actually checked instead of assumed.

§13–§17 — security, conventions, and the final rule

§13
Security

An explicit list of what browser code is never allowed to touch — service-role database keys, background-job secret keys, bot tokens, any third-party API key — plus the inverse: what browser code is never allowed to do (trigger a job without a session check first, write via a privileged client, call a third-party API directly). Then a living env-var table, kept in sync with .env.example, documenting every secret's purpose and exposure:

VariablePurposeExposure
NEXT_PUBLIC_*_URLPublic project URLclient + server
*_SERVICE_ROLE_KEYPrivileged DB access for server actions / jobsserver only
*_SECRET_KEYBackground-job trigger/authserver only
<VENDOR>_API_KEYPer-integration third-party keyserver only
<PROVIDER>_WEBHOOK_SECRETShared-secret webhook verification when the vendor has no HMAC signingserver only

The pattern worth copying isn't the specific rows — it's documenting why each one is shaped the way it is right in the table (e.g. "this vendor has no webhook signing, so this shared secret is the entire verification mechanism"), so a future session never has to reverse-engineer intent from a bare variable name.

§14
API conventions

Prefer server actions for user-initiated mutations; thin API route handlers only for what a server action genuinely can't do (inbound webhooks). Any such route validates its payload with a schema library before touching the database or triggering a job — every external input is untrusted until validated, no exceptions.

§15
Commands & checks

The exact commands "run available checks" means — type-check, lint, a production build when relevant — plus the explicit instruction: report exact command output; do not claim a check passed without running it. That sentence exists because an unsupervised agent will, left to its own judgment, sometimes narrate success instead of demonstrating it. Writing the rule down removes the judgment call.

§16
Extraction plan

A step-by-step checklist for the day a feature has to leave the codebase entirely and become its own standalone app (a client who needs full code ownership, for instance). Worth having even if you never use it: writing it forces you to confirm your own layering rule (§5) is real — if a feature's logic is genuinely isolated in its own files rather than smeared across shared components, extraction is a few days of real but mechanical work. If it isn't, this section is where you'd discover that the hard way instead.

§17
Final rule

The whole file, compressed to a "when in doubt" checklist Claude can hold in working memory without re-reading all 300-odd lines:

When in doubt:
1. Keep it small.
2. Use the relevant skill.
3. Preserve the standing rules (§8–§12) on every new feature.
4. Ask a focused question if needed.
5. Save a prompt before coding.
6. Ask if it's good to execute.
7. Implement after confirmation.
8. Run available checks.
9. Share exact test steps.
05 Where they meet

AGENTS.md doesn't replace the skill chain — it calls it by name

Look back at §2's workflow block: step 7 is "create a prompt file," step 10 names check verify and test explicitly, and the line right after step 11 names check review, sync, and document by their exact command names. The contract file is what makes the generic skill chain project-aware — it tells Claude precisely when, in this specific codebase's lifecycle, each general-purpose skill gets invoked, and what it's allowed to touch when it runs.

WITHOUT AGENTS.md

The skill chain still runs

...but Claude re-derives your architecture rules, your rejected tech choices, and your naming conventions from scratch every session — and will eventually contradict a decision it already made, because nothing wrote that decision down anywhere it re-reads.

WITHOUT THE SKILL CHAIN

AGENTS.md has nothing to enforce

A contract that says "write a prompt file, get approval" is just prose unless something actually structures how that prompt gets written, reviewed, tested, and reconciled afterward. The skills are the enforcement mechanism for the contract's own rules.

TOGETHER

A closed, repeatable loop

Generic process (any project) plus specific memory (this project) is what lets a build stay coherent across dozens of sessions and months of calendar time — which is the actual, boring, unglamorous hard part of building real software with AI.

06 Take it with you

Setting this up on your own project

You don't need a nine-section product spec to start. You need these, in this order.

1

Install the workflow skills

Get the scope/architect/develop/check/test/document/sync chain from jsmastery.com/workflow-guides before writing a single line of your own contract file — it's the enforcement layer the contract needs underneath it.

2

Bootstrap AGENTS.md with /audit, then edit it by hand

Run /audit on your repo root (or one subfolder at a time on an existing codebase) for a first draft, then rewrite §1 and §6 yourself — the product narrative and the rejected-tools reasoning are judgment calls no audit can make for you.

3

Write §2 (workflow) and §4 (prompt-file spec) before anything else

These two sections are what make the approval gate real. Everything else in the file can grow incrementally; these two need to exist from commit one.

4

Lock a skill allowlist and say "do not invent new skills"

List only what this project actually needs, each with a one-line reason specific to this codebase. An unbounded list is functionally the same as no list.

5

Pin the one or two architecture rules your codebase can't survive without

Not an exhaustive style guide — the specific layering or data-isolation rule that, if it drifted even once, would be expensive to unwind later.

6

Write down what you rejected, and why

"Not X — Y would require [specific real cost]" prevents the same debate from reopening a month later with nobody around who remembers the first conversation.

7

Run the full loop once, on purpose, before trusting it

Brainstorm → scope → architect → develop → verify → test → review → document → sync, on one real, small feature. Everything about how the two layers hand off to each other becomes obvious the first time you watch it happen end to end.
